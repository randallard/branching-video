# ADR-0035: Move to pnpm 12, with the lockfile regenerated in its own change
- Status: Accepted
- Date: 2026-10-31
- Deciders: Ryan

## Context
[ADR-1016](1016-pnpm-supply-chain-settings-stay-explicit.md) says a new pnpm *major* is
evaluated in a stance review before `packageManager` moves. pnpm 12 shipped 2026-08-26 (latest
12.17.0, 2026-10-30); this repo pins `pnpm@11.28.10`. The 2026-10-31
[stance review](../reviews/2026-10-31-stance-review.md) did the evaluation, against the v12.0.0
release notes (read for cycle-in the same day, its ADR-0021) and a trial here:

- Nothing in the release notes renames or removes a setting in `pnpm-workspace.yaml`
  (`onlyBuiltDependencies`, `strictDepBuilds`, `minimumReleaseAge`, `trustPolicy`,
  `blockExoticSubdeps`, `overrides`). 12 fails the install on an unrecognised setting; on the
  trial it didn't.
- On a throwaway `git archive` export, outside the repo with scripts off
  ([ADR-0012](0012-block-install-time-scripts.md)), pnpm 12.17.0 installed, and lint, 145
  tests and the build passed.
- A `--frozen-lockfile` install fails when only `packageManager` changes: in 12 the package
  manager is itself a lockfile entry (`packageManagerDependencies`), and the lockfile drops its
  `settings:` block. So the move rewrites the lockfile.
- That lockfile is two YAML documents. osv-scanner before v2.7.0 reads only the first and
  passes while scanning none of our packages
  ([ADR-1018](1018-osv-scanner-reads-the-whole-lockfile.md)). CI here is already on v2.7.0,
  which read all 308 on the trial.

Ryan asked for the move.

## Decision
Move to **pnpm 12** (the current 12.x when the change is made): `packageManager` to it,
`engines.pnpm` to `>=12`, and the lockfile regenerated by pnpm 12, in **one change of its own**
that does nothing else, so the lockfile diff reads as a format change and any dependency that
resolves differently stands out.

Before it merges it passes every gate the trial couldn't run: CI itself (where
`pnpm/action-setup` reads `packageManager`), `pnpm audit`, `pnpm audit signatures`, the licence
allowlist, the axe pages, and the OSV scan of the new lockfile with the package count checked,
not just "no issues".

## Alternatives considered
- **Stay on 11.x.** Workable for now, but 11 will leave support, and the move only gets bigger
  as the lockfile ages.
- **Let Renovate propose it.** Which pnpm Renovate would run to rewrite the lockfile across a
  major is untested here, and a major's lockfile rewrite deserves a change made and read on
  purpose, not one batched among routine updates.

## Consequences
- Contributors and CI need pnpm 12. `engines.pnpm >=12` says so; `packageManager` lets
  Corepack and `pnpm/action-setup` pick it up.
- The supply-chain settings carry over unchanged.
- pnpm 12 ships as a native binary that its npm package fetches on first run. The lockfile now
  records those binaries with integrity hashes, but where they come from is pnpm's to attest.
- The OSV pin must not drop below v2.7.0; the comment on it in `ci.yml` says why.
- Promotion condition: none beyond ADR-1016's (evaluate 13 in a stance review first).
