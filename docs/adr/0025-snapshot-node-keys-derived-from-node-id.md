# ADR-0025: Snapshot node keys are derived from the node's id, with a content-hash fallback
- Status: Accepted
- Date: 2026-09-15
- Deciders: Ryan

## Context
A node in the event log is identified by a `nodeKey`, and every `node-field-set`,
`node-choices-set` and `node-removed` targets one. `node-added` carries its key explicitly, so it
poses no question. A `show-snapshot` does: it carries a whole `ShowConfig`, and a config's nodes
have no `nodeKey` — [ADR-0010](0010-config-json-stays-the-publish-and-interchange-format.md) froze
that format, and it is the file people hand-write and publish. So the keys must be derived.

They must also be derived **identically on every device**, and the reason is stronger than it
first looks. [ADR-0011](0011-legacy-drafts-and-backups-import-as-snapshot-events.md) makes the
snapshot's event id a hash of `(showId, canonical config)` so that importing the same content
twice is a no-op anywhere. That id covers the config, not the keys. So if a snapshot event carried
keys generated by whoever created it, two devices importing the same file would produce events
with **the same id and different payloads**, and dedupe — first copy wins — would resolve them by
arrival order. Keys therefore have to be a pure function of the config's content; carrying them in
the event is not merely awkward, it is incoherent with the id scheme.

That leaves the question of *which* function of the content, and the candidates fail differently:

- **Position** does not survive reordering. Re-import a file whose nodes moved and every key points
  at a different node, so every prior per-field edit silently lands on the wrong one.
- **A hash of the whole node** does not survive an edit: change a title and the node becomes a
  different node at the next snapshot. Identical nodes also collide.
- **The node's `id`** survives both of the things that actually happen to a show — an updated file
  being re-imported, and nodes being reordered.

The case that makes this concrete, and that is easy to miss: a laptop re-imports an updated file
(snapshot 2, 10:00) while a phone edits a node's title (10:05). On merge the phone's edit targets a
key derived from snapshot 1. Under a positional or content-hash rule that key is absent from
snapshot 2 and **the phone's edit does nothing, silently**. Under an id-derived rule the key
survives the re-import, and the edit lands. Re-importing an updated file is the main reason a
second snapshot exists at all (ADR-0011's update-or-add), so this is the common path.

[ADR-0009](0009-show-identity-by-generated-id-not-slug.md) rules an editable field out as a
*show's* identity, which looks like an objection. It isn't: this is a derivation performed once, at
snapshot time, and the key is frozen there. Renaming a node's id afterwards is an ordinary
`node-field-set` that leaves the key untouched.

## Decision
A snapshot's node keys are derived from the node's own `id`: `n:<id>` when that id is unique
within the config.

An id that is duplicated or blank identifies nothing, so those nodes key off a hash of their own
content — `n:<id>:<hash>` or `h:<hash>` — rather than off their position. Nodes that are *fully*
identical necessarily land on the same hash and take an occurrence suffix; that is sound because
identical nodes are interchangeable, and it keeps both rather than collapsing them into one.

## Alternatives considered
- **Position for the whole rule, or as the duplicate fallback** — rejected. Reordering a config
  then repoints keys at the wrong nodes and edits land silently on the wrong one. The fallback
  mattered because snapshots accept unvalidated configs: `normalizeConfig` is deliberately lenient,
  so a config with duplicate ids reaches the reducer even though the validator calls it an error.
- **A hash of the whole node** — rejected: no identity across an edit.
- **Carry the keys in the snapshot event** — rejected as incoherent with ADR-0011's event id, as
  above.
- **Add `nodeKey` to the config format** — rejected: it needs a new ADR superseding ADR-0010, leaks
  an internal storage concern into the published interchange format that the player, `live/` shows
  and cycle-in all consume, and hand-written configs would still need the derivation as a fallback.

## Consequences
- Editing a node's `id` and then re-importing an export of that show is seen as a *different* node:
  the old key disappears with the snapshot that replaced it and a new one appears. Edits landing
  in the window around that re-import can be lost. This is the residual cost of deriving from an
  editable field, and the id is still the most stable thing a config node has.
- Keys are human-readable (`n:intro`), which makes the log and any future history view legible.
  Hash-fallback keys are not, but they only occur in configs the validator already rejects.
- Two fully identical nodes in one config cannot be told apart, so which of them a later edit
  targets is arbitrary. They are interchangeable by construction, so this is a non-problem until
  one of them is edited — at which point they are no longer identical and the next snapshot
  separates them.
- The rule is a pure function of the config and is property-tested for it: reordering a config
  never changes which node a key refers to, and identical nodes both survive.
- **Promotion condition:** if node ids start being renamed routinely — an authoring habit this
  penalises — revisit with an ADR that gives nodes a real identity in the file, which means
  superseding ADR-0010 rather than patching this.
